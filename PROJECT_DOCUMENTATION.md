## 1. Project Overview

### What it is

**AI Software Architect** is a full-stack web application. A user types a description of a software project idea (e.g. "a food delivery app" or "an AI healthcare assistant") into a form, picks an expected user scale (Small / Medium / Large / Enterprise), and clicks **Generate Architecture**. Within roughly 20–30 seconds, the system produces:

- Functional and non-functional **requirements**
- A recommended **system architecture** (pattern, core services, key REST endpoints)
- A **database design** (tables, relationships, an indexing recommendation)
- A **DevOps plan** (test cases, security risks + mitigations, a rough build timeline)
- On request, any of **17 different engineering diagrams** (System Architecture, ER Diagram, Use Case, Sequence, Class, Activity, State, Component, Deployment, Data Flow, Microservices Communication, Network Architecture, Security Architecture, CI/CD Pipeline, SDLC Workflow, User Journey, API Interaction, Infrastructure) — rendered as real, visual diagrams, downloadable as PNGs

All of this is saved permanently, browsable later from a **History** view, and the whole system is deployed live on the public internet.

### What problem it solves

Turning a rough idea into a first-draft architecture document is normally slow, manual work — usually done by a senior engineer or architect sketching things out over hours or days. This project automates that first draft: instead of starting from a blank page, a founder, student, or engineer gets a structured, scale-aware starting point in under a minute, which they can then refine.

### Why it was built

This started as a personal capstone/portfolio project, built from scratch by a computer science student with some prior coding experience but no prior experience with Spring Boot, Docker, or deploying a multi-service application. The explicit goal from the very first message was to **learn by building** — every piece was explained conceptually before being implemented, with the assistant (Claude) acting as a patient, step-by-step teacher rather than just writing code and handing it over.

### Main goal

Build a genuinely working, deployed, multi-agent AI system — not a toy demo — that:

- Demonstrates real full-stack engineering (Java/Spring Boot backend, React frontend, Python ML microservice, PostgreSQL database)
- Demonstrates real AI-agent orchestration (multiple specialized prompts/agents coordinated by one backend service)
- Is deployed and shareable, not just something that runs on one person's laptop
- Comes with a documented, honest account of what was built and how — suitable for a college project review and for technical interviews

## 2. Project Journey — Start to Finish

This section tells the story chronologically — including the false starts, the debugging, and the decisions that changed along the way. The architecture section (Section 3) describes the _end state_; this section describes _how we got there_.

### 2.1 The starting point: an oversized blueprint

The project began with a very large, pre-written "complete implementation blueprint" document — a multi-thousand-line spec proposing a full enterprise system: Spring Boot backend, a Python ML microservice with a scikit-learn classifier, a ChromaDB RAG knowledge base, PlantUML diagram generation, Docker Compose, and more.

The first real decision was **not to build all of it blindly**. The blueprint was reviewed critically first — strengths (scale-aware design, sensible agent decomposition, reasonable DB schema) and weaknesses (an outdated Gemini model name, disabled security, brittle JSON parsing of LLM output, synchronous `.block()` calls defeating the point of using reactive WebClient) were both called out before any code was written. The scope was then deliberately narrowed to start with just the ML service, prove it worked end to end, and build outward from there — rather than attempting the entire blueprint in one pass.

### 2.2 Environment setup (MacBook Air M1)

Before any code, the development environment was set up and verified:

- Homebrew, Git, Python 3.14, Java 22, and Node 25 were already present on the machine
- **PostgreSQL 16** was installed via Homebrew, started as a background service, and a database (`ai_software_architect`) was created
- **Docker Desktop** was installed for later containerization

A recurring theme from the very start: the user explicitly asked that **Git/GitHub instructions only be surfaced at major checkpoints**, not after every small step — this shaped the whole session's rhythm of "build → verify → checkpoint," rather than committing after every single file.

### 2.3 Building the ML service first

The Python ML microservice (FastAPI) was built and proven working **before** any Java code was written, specifically so there would be one small, fully working piece before adding complexity:

- A **TF-IDF + Logistic Regression classifier** trained on a ~80-row hand-written CSV dataset spanning 10 requirement categories (Authentication, Payment, Database, Frontend, Backend, Cloud, Notification, Recommendation, Analytics, Integration)
- A **ChromaDB (embedded) vector store** seeded with 10 hand-written architectural pattern documents, spanning four scale levels (Small/Medium/Large/Enterprise), queryable via a `/rag/query` endpoint
- A FastAPI app exposing `/classify`, `/classify/batch`, `/rag/query`, and `/health`

**Two real installation problems came up immediately** because the machine's Python (3.14) was newer than the pinned package versions in the original blueprint:

1. `pip install` failed on several packages with no matching distribution for the exact pinned versions → fixed by relaxing `requirements.txt` from exact pins (`==`) to minimum versions (`>=`)
2. `pydantic-core` (a Rust-backed dependency) failed to compile against Python 3.14 because of a removed internal Python API → resolved itself once the version constraint was relaxed and a newer `pydantic-core` build (with real 3.14 support) was installed instead

Once installed, the classifier was trained and manually tested (`"reset password via email"` → `AUTHENTICATION`, 66% confidence), and the FastAPI server was started. A subtle bug appeared here: running `uvicorn` directly picked up a **different, global** installation instead of the one inside the project's virtual environment, because a global copy sat earlier in the shell's `PATH`. The fix — `python3 -m uvicorn` instead of bare `uvicorn` — became a running pattern throughout the project (also relevant later for `pip`/`python3` mismatches).

With `/health`, `/classify`, and `/rag/query` all confirmed working via `curl`, this was pushed as **Checkpoint 1** to a new GitHub repository.

### 2.4 Building the Spring Boot backend, piece by piece

The Java backend was generated via **Spring Initializr** (Java 17, Maven, with Spring Web, Spring Data JPA, PostgreSQL Driver, Validation, and Lombok), opened in **VS Code** (not IntelliJ — the user's existing tool of choice).

An early false alarm: VS Code's Java language server showed "cannot find symbol" errors for Lombok-generated getters/setters, even though `mvn clean compile` succeeded cleanly. This was diagnosed as a **cosmetic IDE cache issue**, not a real compile problem, and was worked around (partially resolved via "Java: Clean Java Language Server Workspace") without blocking progress.

The backend was then built up in small, independently-tested layers:

1. A minimal `HelloController` with a `GET /` endpoint returning `"Backend is alive!"` — to prove Tomcat and routing worked at all
2. `MlServiceClient` (using Spring WebFlux's `WebClient`) calling the ML service's `/health` endpoint — proving cross-service HTTP communication, exposed via `GET /check-ml`
3. A `Project` JPA entity, `ProjectRepository`, and `POST /projects` / `GET /projects` / `GET /projects/{id}` endpoints — proving real database persistence against local Postgres

This was **Checkpoint 2**.

### 2.5 Wiring in Gemini

A free Gemini API key was created and stored as an environment variable (`GEMINI_API_KEY`), never hardcoded. This immediately surfaced a genuinely tricky, very common Mac issue: **apps launched from the Dock/Finder don't inherit environment variables set in a terminal session** — so VS Code, when opened by clicking its icon, couldn't see the key even though `echo $GEMINI_API_KEY` worked fine in Terminal. The fix was to always launch VS Code _from_ a terminal that had the variable set (`code .`), and to run the backend from VS Code's _integrated_ terminal rather than its separate "Run" button (which uses its own launcher and doesn't reliably inherit the shell environment either).

Once the key was flowing correctly, `GeminiService` was built with a hardcoded model name from the original blueprint (`gemini-1.5-flash`), which immediately failed with a `404` — investigation (via direct `curl` calls to Gemini's API, bypassing the Java code entirely to isolate the problem) revealed Google had deprecated that model, and then the next attempt (`gemini-2.5-flash`), and the next (`gemini-2.5-flash-lite`), for new API keys specifically. The actual working model turned out to be **`gemini-3.6-flash`**, confirmed directly via `curl` before touching any Java code again — a deliberate debugging pattern used repeatedly through the project: **isolate the smallest failing piece outside the full stack before changing code**.

With `/test-gemini` returning real generated text, the first true AI feature was built: `RequirementAnalystAgent`, exposed as `GET /projects/{id}/analyze`, taking a saved project's description and scale and asking Gemini (with a role-based, structured prompt) to return numbered functional and non-functional requirements. Confirmed working, this became **Checkpoint 3**.

### 2.6 The other three agents, and orchestration

The same pattern — `@Component` agent class, constructor-injected `GeminiService`, a role-based prompt with placeholders — was repeated to build:

- `SystemArchitectAgent` (architecture pattern, core services, key REST endpoints)
- `DatabaseArchitectAgent` (tables, relationships, an indexing recommendation)
- `DevOpsPlannerAgent` (test cases, security risks + mitigations, a rough timeline)

All four were confirmed individually working (**Checkpoint 4**), and the controller was refactored to remove repeated "fetch project or throw" logic into one private helper method (`getProjectOrThrow`) — an early, explicit application of the **DRY (Don't Repeat Yourself)** principle.

Then came `OrchestrationService`: one method that calls all four agents **sequentially** (each waiting for the previous Gemini call to finish) and saves the combined result as one `ArchitectureResult` row, linked one-to-one with its `Project`. Exposed as `POST /projects/{id}/generate`, this became the system's single most important endpoint, confirmed working end to end and saved to Postgres (**Checkpoint 5**).

### 2.7 The React frontend

A React app (Vite, plain JavaScript, ESLint — not TypeScript) was scaffolded and built as a single form: project name, description, a scale dropdown, and a "Generate Architecture" button, calling `POST /projects` then `POST /projects/{id}/generate` and rendering the four resulting text sections.

The very first end-to-end browser test immediately hit a **CORS error** — the browser blocking requests from `localhost:5173` (the frontend) to `localhost:8080` (the backend), since browsers restrict cross-origin requests by default (unlike `curl`, which isn't a browser and isn't subject to this rule). This was fixed with a `WebConfig.java` explicitly allowlisting the frontend's origin. With that fixed, the first full browser-driven generation succeeded (**Checkpoint 6**).

### 2.8 Docker Compose — several real infrastructure problems

Dockerfiles were written for all three services (multi-stage builds for the Java backend and the React+Nginx frontend), plus a `docker-compose.yml` tying together Postgres, the ML service, the backend, and the frontend.

This phase surfaced the most infrastructure-level debugging of the whole project:

- `eclipse-temurin:17-jre-alpine` had **no published arm64 build**, confirmed by directly `docker pull`-ing the exact tag and reading the real error (`no matching manifest for linux/arm64/v8`) rather than assuming it was a network issue — fixed by switching to the non-Alpine `eclipse-temurin:17-jre` tag, which does support arm64
- The ML service's embedding model (`all-MiniLM-L6-v2`, ~79MB) kept timing out mid-download _inside the container_ on a slow/unstable connection, repeatedly, across multiple full rebuild attempts — fixed by pre-downloading it **during the Docker image build** using `curl` with an explicit resume/retry policy (`--retry 15 --retry-delay 5 --continue-at -`), so the running container never needs network access for it again
- After apparently fixing everything, the ML container was found to exit immediately and silently (`docker ps` showed `Exited (0)`, with the container's actual startup command showing as just `"python3"`) — diagnosed as a **missing `CMD` instruction**, accidentally dropped from the Dockerfile during earlier edits, causing the base image's default (a bare interactive Python shell with no input) to run instead

Once all three were resolved, `docker-compose up` successfully started all four containers together, and the full pipeline was retested through the containerized stack (**Checkpoint 7**).

### 2.9 Polish: styling and a loading animation

The frontend was given a dark theme, gradient title, and card-based layout (Checkpoint 8), followed by an animated 4-dot "multi-agent working" loader with rotating status text cycling through each agent's name — a deliberate choice to make the ~20-second wait feel purposeful rather than like a stalled page.

### 2.10 Git collaboration workflow

In anticipation of working with teammates, a proper collaboration workflow was set up: GitHub collaborators, **branch protection on `main`** (requiring Pull Requests, disallowing direct pushes), and an initial project `README.md` written and merged through the exact branch → PR → merge flow that teammates would use.

### 2.11 The diagram generation feature (the biggest single feature)

The user requested a large feature: automatically generating real, rendered engineering diagrams (not just text) — eventually specified as a full 20+ diagram type list (all major UML diagrams, DFD, network/security architecture, CI/CD, SDLC, and more), with the explicit request that this be attempted in full rather than a token 2–3-diagram version.

Rather than writing 20 near-duplicate agent classes, this was built as **one reusable engine**:

- `DiagramAgent` — a single, generic, parameterized agent: given a diagram type name, a short syntax guide, and the project's description/scale, it prompts Gemini to output **Mermaid.js syntax** (a text-based diagram language covering flowcharts, sequence diagrams, class diagrams, ER diagrams, state diagrams, and more from one rendering library) and strips any stray markdown code fences from the response
- `DiagramTypeRegistry` — a static lookup map from a URL-friendly type key (e.g. `"system-architecture"`) to a `(display name, syntax guide)` pair — the single place new diagram types get added
- One generic endpoint, `POST /projects/{id}/diagrams/{type}`, serving all 17 types by looking up the right spec from the registry

Two entities were added: `Diagram` (many-to-one with `Project`, since a project ends up with many diagrams) and its repository. The first type (System Architecture) was proven working end to end before the registry was expanded to all 17 — including hitting and fixing a classic **three-part dependency-injection mistake** (field declared, constructor parameter added, but the actual `this.x = x;` assignment line forgotten — causing a "blank final field may not have been initialized" compile error).

The frontend side added `mermaid.js`, a reusable `DiagramViewer` React component (rendering Mermaid text into real SVG via `mermaid.render()`, with graceful error handling for malformed syntax), and a row of 17 buttons. Midway through wiring this up, a serious regression occurred: an edit accidentally **deleted the entire `handleGenerate` function and the results-display block** from `App.jsx`, silently breaking the whole page (`Uncaught ReferenceError: handleGenerate is not defined`) — diagnosed via the browser console and fixed by restoring the complete file in one pass, rather than another incremental patch (**Checkpoint 10** once fully confirmed working).

### 2.12 Persistence, PNG export, and delete

Three further features rounded out the local build:

- **`GET /projects/{id}/diagrams`** to fetch a project's already-generated diagrams, and frontend logic to auto-load them so refreshing/revisiting a project doesn't lose previously generated (and already paid-for, in API calls) diagrams
- **PNG export** for any rendered diagram — drawing the SVG onto an HTML `<canvas>` at 2× scale and exporting as a PNG. This hit a genuine browser security wall (`SecurityError: Tainted canvases may not be exported`) caused by loading the source SVG via a `Blob` URL; fixed by switching to a base64 **data URI** instead, which doesn't trigger the same-origin ambiguity that taints a canvas
- **Delete project**, implemented as a `@Transactional` cascade (diagrams → architecture result → project, in that dependency order) with a frontend confirm dialog — this surfaced a **duplicated interface definition** left inside `DiagramRepository.java` from an earlier edit (the old and new versions of the interface both present in one file), which cascaded into ~22 unrelated-looking Lombok compile errors until the file was rewritten cleanly

### 2.13 A large, unrelated diagram-feature request

At one point, a very large, separately-drafted "Automatic Diagram Generation Engine" feature spec was pasted in — proposing dynamic per-project diagrams, 20+ types, and export to PNG/SVG/PDF/Mermaid/PlantUML/Draw.io/Lucidchart. This was reviewed honestly: the _diagram-generation_ half of it was, in substance, what had already been built (the generic `DiagramAgent` + `DiagramTypeRegistry` engine); the _multi-format export_ half (PDF, Draw.io, Lucidchart) was explicitly scoped out as unrealistic to add well in the time available, beyond the PNG export already built.

### 2.14 Deployment — Neon + Render

The stack was deployed to **Render** (three separate Docker-based web services) and **Neon** (a managed Postgres provider chosen specifically because Render's own free-tier Postgres expires after 30–90 days, while Neon's free tier does not).

Deployment surfaced its own round of real problems:

- A first attempt at the Neon connection string setup was lost/misplaced, requiring the whole Neon setup to be redone
- The user **accidentally pasted their real database password into chat** — handled immediately by resetting the Neon password before continuing, rather than treating it as a minor slip
- `MlServiceClient`'s base URL was hardcoded to `localhost:8000`, which obviously doesn't exist on Render's servers — fixed by making it configurable via `@Value("${app.ml-service.url:http://localhost:8000}")`, with the colon-syntax default preserving local development behavior unchanged
- The backend's first deploy failed with `Unable to determine Dialect without JDBC metadata` — traced to the whole Neon connection string being pasted into one Render environment variable field instead of being split into separate URL/username/password fields as Spring Boot expects
- After a successful deploy, `/check-ml` returned `500` — traced to a **missing `APP_ML_SERVICE_URL` environment variable** on the deployed backend (defaulting back to the useless `localhost:8000`), fixed by adding it
- The frontend had `http://localhost:8080` hardcoded in every `fetch()` call — fixed by introducing `VITE_API_URL` (read via `import.meta.env`, with a `localhost:8080` fallback for local dev) and a `.env.production` file setting it to the real deployed backend URL at build time
- The backend's CORS allowlist needed the real deployed frontend origin added alongside `localhost:5173`

Once all of this was resolved, the **full pipeline was confirmed working entirely in the cloud** — a real generated project, real diagrams, no `localhost` or Docker involved anywhere.

### 2.15 Post-deployment bug fixes

A few issues only appeared once live traffic patterns differed from local testing:

- Loading a History project that had been created but never successfully generated **crashed the frontend** (`Unexpected end of JSON input`), because `response.json()` was called unconditionally on what could be an empty response body — fixed by reading the response as text first and only parsing it as JSON if non-empty
- The **User Journey** diagram type occasionally produced invalid Mermaid syntax (a parser error referencing `taskData`, since Mermaid's `journey` and `gantt` diagram types share underlying grammar) — fixed by rewriting that diagram type's prompt to include a **literal, concrete example** of correct syntax rather than only a written description, since LLMs follow concrete examples more reliably than abstract instructions
- A **stale browser cache** after a redeploy caused one diagram type to fail with "Failed to fetch dynamically imported module" (Mermaid loads some renderers as separate hashed files, and an old cached page referenced filenames that no longer existed after the rebuild) — resolved with a hard refresh
- Generating diagrams for **Large/Enterprise-scale projects** intermittently failed with `500` errors, traced via live Render logs to genuine Gemini free-tier rate limiting (`429 Too Many Requests`) — caused by the frontend allowing multiple diagram buttons to be clicked in quick succession, firing overlapping Gemini calls. Fixed with two changes: the frontend now disables **all** diagram buttons while any one diagram is generating (serializing requests instead of allowing bursts), and the backend's retry logic was made more patient (5 retries with a 3-second exponential backoff base, instead of 3 retries at 2 seconds) so a single request is more likely to succeed by waiting out one rate-limit window

With these fixed, the deployed system was confirmed working correctly across all four scale levels.

### 2.16 Post-deployment cleanup: removing the unused RAG code

While writing this documentation, an honest gap surfaced: the ML service's ChromaDB-based RAG component had been built and independently tested, but was never actually called by any agent during real generation — only a health check was wired into the backend. Two paths were considered: actually integrate it into the agent prompts, or remove it as unused. Since it was genuinely unused _and_ was the single biggest source of Docker/deployment friction earlier in the project (the large embedding-model download that required custom retry logic just to build reliably), the decision was made to **remove it entirely** rather than keep dead code around or half-integrate it under time pressure.

This meant deleting `rag/vector_store.py`, removing the `chromadb` dependency, removing the `/rag/query` endpoint and its Pydantic models from `app.py`, and simplifying the Dockerfile back down to just training the classifier — no more `curl`-based pre-download step. Verified locally (`/health`, `/classify` still correct; `/rag/query` now a clean `404`) before pushing, then confirmed on the live Render deployment via clean startup logs showing no vector-store initialization step at all.

### 3.2 Data flow: from a project description to a finished architecture

1. User submits the form → frontend sends `POST /projects` → backend saves a `Project` row in Postgres and returns it (with a generated UUID)
2. Frontend immediately sends `POST /projects/{id}/generate` → backend's `OrchestrationService` runs, calling four agents **in sequence**:
   - `RequirementAnalystAgent` → Gemini → functional/non-functional requirements text
   - `SystemArchitectAgent` → Gemini → architecture pattern, services, endpoints text
   - `DatabaseArchitectAgent` → Gemini → tables, relationships, indexing text
   - `DevOpsPlannerAgent` → Gemini → test cases, security risks, timeline text
3. All four text blocks are combined into one `ArchitectureResult` row (one-to-one with the `Project`) and saved
4. The combined result is returned to the frontend and rendered as four sections
5. If the user clicks a diagram button, the frontend sends `POST /projects/{id}/diagrams/{type}` → the backend looks up that type's prompt spec in `DiagramTypeRegistry`, calls the generic `DiagramAgent` → Gemini → Mermaid.js syntax text, saves it as a `Diagram` row (many-to-one with the `Project`), and returns it
6. The frontend's `DiagramViewer` component renders the returned Mermaid text into a real SVG diagram in the browser using `mermaid.render()`
7. The **History** tab lists every saved project (`GET /projects`); clicking one fetches its saved result (`GET /projects/{id}/result`) and saved diagrams (`GET /projects/{id}/diagrams`) and displays them without calling Gemini again
8. **Delete** (`DELETE /projects/{id}`) removes a project's diagrams, its architecture result, and the project itself, in that order, inside one database transaction

## 4. Technology Stack

| Layer                     | Technology                                   | Used for                                          | Why chosen                                                                                                                                                                                                 |
| ------------------------- | -------------------------------------------- | ------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Frontend                  | React 19 (Vite, JavaScript)                  | UI, form, results/diagram rendering               | Fast dev server, modern standard tooling; plain JS chosen over TypeScript to keep learning scope manageable                                                                                                |
| Frontend diagrams         | mermaid.js                                   | Rendering AI-generated diagram text into real SVG | Text-based diagram syntax covering many diagram types (flowchart, sequence, ER, class, state, journey, gantt) from one library — makes a 17-type diagram engine tractable with a single rendering approach |
| Frontend styling          | Plain CSS (no framework)                     | Dark theme, card layout, animations               | Small enough surface area that a framework wasn't necessary                                                                                                                                                |
| Backend                   | Spring Boot 4 / Java 17                      | REST API, orchestration, persistence              | Requested learning target; industry-standard for enterprise-style Java backends                                                                                                                            |
| Backend HTTP client       | Spring WebFlux `WebClient`                   | Calling Gemini and the ML service                 | Non-blocking client with built-in exception types (e.g. `WebClientResponseException.TooManyRequests`) used directly for retry logic                                                                        |
| Backend ORM               | Spring Data JPA + Hibernate                  | Entity ↔ database mapping                         | Standard Spring persistence layer; `JpaRepository` gives free CRUD + derived-query methods (`findByProjectId`, `deleteByProjectId`) from method names alone                                                |
| Boilerplate reduction     | Lombok                                       | Auto-generating entity getters/setters            | Avoids hand-writing repetitive accessor methods                                                                                                                                                            |
| Database (local)          | PostgreSQL 16 (Homebrew, then Docker)        | Local development persistence                     | Matches the production database engine                                                                                                                                                                     |

## 5. Features

| Feature                                           | How it works internally                                                                                                                                                                                                                                                                                                                   |
| ------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Generate full architecture from a description** | `POST /projects` creates the row; `POST /projects/{id}/generate` runs `OrchestrationService`, which calls all 4 core agents sequentially and saves one combined `ArchitectureResult`                                                                                                                                                      |
| **4 specialized AI agents**                       | Each agent is a small `@Component` class holding one role-specific prompt template with placeholders for the project description and scale; all share the same underlying `GeminiService`                                                                                                                                                 |
| **Scale-aware output**                            | The user's chosen scale (`SMALL`/`MEDIUM`/`LARGE`/`ENTERPRISE`) is interpolated directly into every agent's prompt, so Gemini's recommendations (e.g. monolith vs. event-driven microservices) change with it                                                                                                                             |
| **17 engineering diagram types**                  | One generic `DiagramAgent` + a `DiagramTypeRegistry` lookup map + one generic `POST /projects/{id}/diagrams/{type}` endpoint serve all 17 types — adding a new type is a matter of adding one entry to the registry, not writing new Java classes                                                                                         |
| **Real diagram rendering**                        | The backend returns raw Mermaid.js text; the frontend's `DiagramViewer` component calls `mermaid.render()` to turn that text into an actual SVG shown in the page                                                                                                                                                                         |
| **PNG diagram export**                            | The rendered SVG is drawn onto an HTML `<canvas>` at 2× scale (for sharpness) with a solid dark background (SVGs are transparent by default) and exported via `canvas.toBlob(...)`; loaded via a base64 data URI rather than a Blob URL to avoid a browser "tainted canvas" security restriction                                          |
| **Project history**                               | `GET /projects` lists every saved project, sorted newest-first; clicking one calls `GET /projects/{id}/result` and `GET /projects/{id}/diagrams` and displays the saved content without any new Gemini calls                                                                                                                              |
| **Delete project**                                | `DELETE /projects/{id}` is `@Transactional` and removes, in dependency order, all diagrams, the architecture result, and finally the project row itself                                                                                                                                                                                   |
| **Animated loading state**                        | While `/generate` is in flight, the frontend shows 4 bouncing dots (staggered CSS animation delays) with status text that cycles through each agent's name every 4 seconds                                                                                                                                                                |
| **Rate-limit resilience**                         | `GeminiService` retries on `429 Too Many Requests` up to 5 times with exponential backoff (3s → 6s → 12s → 24s → 48s); the frontend also serializes diagram generation (disabling all diagram buttons while one is in flight) to avoid firing overlapping requests that would trigger the rate limit in the first place                   |
| **Environment-aware configuration**               | Both the ML service URL (backend, via `@Value` with a `localhost` default) and the backend API URL (frontend, via `VITE_API_URL` with a `localhost` default) are configurable per-environment, so the exact same code runs unmodified locally, in Docker, and in production                                                               |
| **Standalone ML microservice**                    | A separate Python/FastAPI service exposes a trained requirement classifier, independently deployed and callable — originally also included a ChromaDB RAG component, deliberately removed after being identified as unused dead weight (see §2.16); not currently called during the main generation pipeline beyond a health check (§3.5) |

### 6.3 The diagram type registry (excerpt)

Each of the 17 entries follows this shape — a URL key mapped to a display name and a syntax instruction for Gemini:

```java
TYPES.put("er-diagram", new DiagramSpec(
    "Entity Relationship Diagram",
    "Use Mermaid erDiagram syntax. Show 3-6 core tables with key columns and " +
    "relationships (one-to-many, many-to-many) using proper crow's foot notation."
));
```

The full list of 17 keys: `system-architecture`, `er-diagram`, `use-case`, `sequence-main-flow`, `class-diagram`, `activity-diagram`, `state-diagram`, `component-diagram`, `deployment-diagram`, `dfd-context`, `microservices-communication`, `network-architecture`, `security-architecture`, `cicd-pipeline`, `sdlc-workflow`, `user-journey`, `api-interaction`, `infrastructure-diagram`.

### 6.4 AI / ML pipeline details

- **Core agents (4):** each sends one Gemini `generateContent` request per call, with a system-style prompt describing a professional role (e.g. "You are a Senior Requirements Analyst") plus the project's description and scale interpolated in
- **Diagram agent (1, reused 17 ways):** same idea, but the prompt also specifies which Mermaid syntax family to use and, for `user-journey` specifically, includes a literal example block after that diagram type repeatedly produced invalid syntax
- **Retry/backoff:** implemented directly in `GeminiService.generate()` — a `for` loop catching `WebClientResponseException.TooManyRequests` specifically (not other exception types), sleeping via `Thread.sleep()`, and doubling the wait each attempt
- **ML service model:** TF-IDF vectorizer (`ngram_range=(1,2)`, `sublinear_tf=True`) feeding a `LogisticRegression` classifier (`class_weight='balanced'`) trained on the ~80-row dataset; **not currently invoked by any agent** (see §3.5 and §11)

### 6.5 Authentication / security

**None implemented.** Every endpoint is publicly accessible with no login, API key, or per-user data isolation. CORS is configured to restrict _which frontend origins_ can call the API from a browser, but this is not authentication — it doesn't prevent direct API calls from tools like `curl` or Postman. This is explicitly listed as a limitation in §11.

### 6.6 Deployment / infrastructure

- **`ml-service`** → Render Web Service, Docker runtime, root directory `ml-service/`
- **`backend`** → Render Web Service, Docker runtime, root directory `backend/`, environment variables: `SPRING_DATASOURCE_URL`, `SPRING_DATASOURCE_USERNAME`, `SPRING_DATASOURCE_PASSWORD` (all pointing at Neon), `GEMINI_API_KEY`, `APP_ML_SERVICE_URL`
- **`frontend`** → Render Web Service, Docker runtime (multi-stage: Node build → Nginx serve), root directory `frontend/`, with `VITE_API_URL` baked in at build time via `.env.production`
- **Database** → Neon (managed Postgres, free tier, no expiration)
- All three Render services auto-redeploy on every push to `main` (GitHub-connected)
- Free-tier Render services **sleep after 15 minutes of inactivity**; the first request after sleeping takes roughly 30–60 seconds to respond (cold start) — expected behavior, not a bug

## 8. Important Design Decisions

**Generic `DiagramAgent` + registry, instead of 20 separate agent classes.**
The alternative — one Java class per diagram type — would have meant ~20 nearly-identical files differing only in their prompt text. Making the diagram type and its syntax guide _data_ (in `DiagramTypeRegistry`) rather than _code_ means adding an 18th diagram type is a one-line addition, not a new class, constructor wiring, and endpoint.

**Sequential agent calls in `OrchestrationService`, not parallel.**
The four core agents currently run one after another, each waiting for the previous Gemini call to finish (hence the ~20–30 second generation time). This was a deliberate simplicity choice for a first working version — parallelizing them (e.g. with `CompletableFuture` or reactive composition) is a known, listed future improvement, not an oversight, but it also would have made the already-tight Gemini rate limit easier to exceed.

**Mermaid.js text syntax as the diagram representation, generated by the LLM itself.**
Rather than trying to have the LLM output structured data that a separate diagram-drawing service converts to an image, Mermaid's plain-text diagram language lets Gemini generate the diagram _directly_, and one JavaScript library on the frontend renders any of the 17 types. The tradeoff is that malformed syntax (as happened with User Journey) fails ungracefully unless specifically handled — accepted as a reasonable tradeoff given the alternative's much higher complexity.

**Neon instead of Render's own free Postgres.**
Render's free-tier database expires after 30–90 days and is deleted; Neon's free tier does not expire. Since the explicit goal was a project that stays usable and demoable long-term (for reviews, interviews, etc.), the extra step of using a separate provider was worth it.

**VS Code instead of IntelliJ.**
IntelliJ is the more common recommendation for Spring Boot specifically, but the user already had VS Code set up and wanted to use their existing tool rather than adopt a new one — a reasonable and explicitly stated preference, worked around (e.g. the Lombok cache issue) rather than treated as a reason to switch.

**Plain CSS instead of a UI framework (e.g. Tailwind, Material UI).**
The frontend's surface area (one form, a results view, a diagram grid, a history list) was small enough that hand-written CSS was faster to reason about and customize than integrating and learning a framework's conventions.

**Exponential backoff retry _and_ frontend request-serialization for rate limits, rather than either alone.**
Backoff alone (Problem #19 in §7) wasn't sufficient once the _frontend_ itself was the source of concurrent bursts. Both the request-generation pattern (frontend) and the failure-recovery pattern (backend) needed fixing together.

**Explicit environment-variable configuration with `localhost` fallbacks, rather than separate config files per environment.**
Both `MlServiceClient`'s target URL and the frontend's `API_URL` use a "read from environment, else default to localhost" pattern. This keeps local development, Docker Compose, and the live Render deployment all running from the _same_ code with no manual edits required when switching contexts — at the cost of that fallback silently masking a missing production variable if forgotten (as happened once, Problem #16).

**Full 20+ diagram type request accepted, but multi-format export (PDF/Draw.io/Lucidchart) explicitly declined.**
When a much larger feature spec was proposed mid-project (§2.13), the diagram-generation part was judged achievable and was built in full (17 real, working types); the additional export-format requests were explicitly scoped out as unrealistic to implement well in the remaining time, rather than attempted superficially.

## 9. Final Project Workflow

Plain-English, end-to-end walkthrough of what happens when someone actually uses the live app:

1. A visitor opens the live frontend URL in their browser.
2. They type a project name, a free-text description of their app idea, and pick an expected scale from a dropdown.
3. They click **Generate Architecture**. The frontend first sends the project details to the backend to create a saved project record, then immediately asks the backend to generate the full architecture for it.
4. Behind the scenes, the backend calls Google's Gemini AI **four separate times**, each time with a different "persona" prompt — a requirements analyst, a system architect, a database architect, and a DevOps lead — each looking at the same project description and scale, each producing its own piece of the puzzle.
5. All four pieces are combined and saved to the database, then sent back to the browser and displayed as four readable sections.
6. Below that, the visitor sees 17 buttons, one per diagram type. Clicking any one of them asks the backend to make one more Gemini call — this time asking specifically for that diagram's content, written in a text-based diagram language — and the result is turned into an actual visual diagram right in the page, with a button to download it as a PNG image.
7. Everything generated is saved permanently. If the visitor comes back later, a **History** tab lists every project they've ever generated; clicking one instantly shows everything that was generated for it before, without waiting or using another AI call.
8. If they no longer want a project, a delete button removes it and everything associated with it for good.

- All backend REST logic currently lives in **one large `HelloController`** class rather than being split into separate controllers (e.g. `ProjectController`, `DiagramController`) — functional, but not how a larger real-world codebase would typically be organized
- `GET /projects` returns **every** project with no pagination — fine at the current data volume, would not scale to a large number of saved projects
- Occasional malformed Mermaid syntax from Gemini is only specifically mitigated for the `user-journey` diagram type; other types could in principle hit similar issues, just haven't been observed to
- Free-tier Render services sleep after 15 minutes idle, causing a slow first request after inactivity
- The database currently contains a number of leftover test/duplicate projects created during development and debugging sessions, never cleaned up
- The four core agents run **sequentially**, not in parallel, making full generation slower than it could be

### Technical debt

- The single large controller class (noted above)
- No dedicated service-layer tests to catch regressions like the ones described in §7 (several bugs were only caught by manual testing after the fact)
- Hardcoded architectural pattern text inside the ML service's RAG store (10 hand-written documents) rather than a larger, more systematically curated knowledge base

## 12. Future Improvements

**Realistic near-term improvements**

- Split `HelloController` into per-resource controllers (`ProjectController`, `DiagramController`, etc.)
- Actually wire the ML service's classifier into the agent prompts, so generated requirements are informed by a real category classification rather than the LLM's unaided output (the RAG half of this idea was removed rather than pursued — see §2.16)
- Add basic automated tests (at minimum, integration tests for the orchestration flow and the diagram generation flow)
- Add pagination to `GET /projects`
- Clean up leftover test data from the database

**Scalability improvements**

- Parallelize the four core agent calls in `OrchestrationService` (they're currently independent of each other and don't need to run sequentially)
- Move off Render/Neon's free tiers if usage grows beyond what they comfortably support
- Add caching for identical/near-identical prompts to reduce redundant Gemini calls

**Performance improvements**

- Stream partial results back to the frontend as each agent finishes, rather than waiting for all four before responding
- Investigate whether a smaller/faster Gemini model tier is acceptable for some of the simpler diagram types

**Security improvements**

- Add real authentication (e.g. JWT-based) and scope projects to the user who created them
- Rate-limit the API itself (not just retry around Gemini's own limit) to prevent abuse of a public, unauthenticated endpoint
- Move the Gemini API key handling fully server-side with tighter secret rotation practices (currently a single long-lived key)

**Additional features**

- Regenerate button for a single failed diagram, rather than requiring a fresh click on the same type
- Export formats beyond PNG (SVG directly, PDF)
- A way to edit/regenerate just one section of a result (e.g. only the database design) without regenerating everything
- Search/filter on the History list

## 13. Interview Preparation

### Basic project questions

**"What does this project do?"**
Key points: takes a plain-text app idea + a scale choice, runs it through 4 specialized AI agents to produce requirements/architecture/database/DevOps text, and can generate any of 17 different rendered engineering diagrams for it — all saved and browsable later, fully deployed live.

**"Who is it for / what problem does it solve?"**
Key points: automates the slow, manual first draft of an architecture document; useful for students, early-stage founders, or engineers who want a fast, structured starting point rather than a blank page.

**"What was your role in building it?"**
Key points: built solo, from environment setup through deployment, learning Spring Boot, Docker, and cloud deployment for the first time during the project; every piece was implemented and tested step by step.

### Architecture questions

**"Walk me through the system architecture."**
Key points: React frontend → Spring Boot backend (Java) → three external dependencies: Postgres (Neon), a Python ML microservice, and the Gemini API. Reference the component diagram in §3.1.

**"Why did you split things into a separate ML microservice instead of putting everything in the Java backend?"**
Key points: demonstrates polyglot service communication (Java calling Python over HTTP); Python/scikit-learn/ChromaDB are more natural choices for the classifier and vector-store work than Java equivalents would have been.

**"How do your services talk to each other?"**
Key points: plain REST/JSON over HTTP; the backend uses Spring WebFlux's `WebClient` for outgoing calls to both the ML service and Gemini.

**"Why is the diagram engine one generic agent instead of 17 separate ones?"**
Key points: the only thing that differs between diagram types is the prompt text; making that data (in a registry) instead of code avoids 17 near-duplicate classes, and adding an 18th type is a one-line change. Reference §8.

### Technology-choice questions

**"Why Spring Boot?"**
Key points: explicit learning goal for the project; industry-standard for backend Java work; strong ecosystem (Spring Data JPA, WebFlux) used directly.

**"Why Gemini instead of OpenAI or another provider?"**
Key points: free tier available for a student project with no ongoing cost; be honest that the model name itself changed twice mid-project as Google deprecated earlier versions — a real example of depending on a fast-moving external API.

**"Why Neon instead of just using Render's own database?"**
Key points: Render's free Postgres expires after 30–90 days and gets deleted; Neon's free tier doesn't expire — important for a project meant to stay demoable long-term.

**"Why Mermaid.js for diagrams instead of, say, generating images directly?"**
Key points: text-based diagram syntax that an LLM can generate directly as part of its text response, rendered client-side by one JS library covering many diagram types — avoids needing a separate image-generation step or service.

### Backend questions

**"How does the orchestration of the 4 agents work?"**
Key points: `OrchestrationService.generateFullArchitecture()` calls each agent's method in sequence, each making its own Gemini call, then combines all four text results into one `ArchitectureResult` entity and saves it in a single write.

**"Why sequential instead of parallel agent calls?"**
Key points: simplicity for a first working version; also somewhat protective against the Gemini rate limit, since parallel calls would burst more aggressively. Explicitly listed as a future improvement, not something overlooked.

**"How do you handle Gemini's rate limiting?"**
Key points: `GeminiService.generate()` catches `WebClientResponseException.TooManyRequests` specifically and retries up to 5 times with exponential backoff (3s base, doubling each attempt); on the frontend, diagram generation is serialized (all buttons disabled while one is in flight) to avoid self-inflicted request bursts in the first place. Reference Problem #19 in §7.

**"How is deletion handled safely across related tables?"**
Key points: `DELETE /projects/{id}` is `@Transactional` and deletes in dependency order — diagrams first, then the architecture result, then the project itself — so a partial failure can't leave orphaned foreign-key references.

### Frontend questions

**"How does a diagram actually get drawn on screen?"**
Key points: the backend returns raw Mermaid.js text; the `DiagramViewer` React component calls `mermaid.render(id, code)`, which returns real SVG markup that's injected into the page via a `ref`.

**"How does PNG export work, given the diagram is an SVG?"**
Key points: the SVG is serialized to a string, base64-encoded into a data URI, loaded into an `<Image>`, drawn onto an off-screen `<canvas>` at 2× scale over a solid background fill, then exported via `canvas.toBlob()` and triggered as a file download.

**"Why did you hit a 'tainted canvas' error, and how did you fix it?"**
Key points: loading the SVG via a `Blob` URL made the browser treat the canvas as possibly containing cross-origin data, blocking pixel-level export as a security measure; switching to a base64 data URI for the same content avoided that restriction entirely. Reference Problem #12.

**"How does your app know which backend URL to call in different environments?"**
Key points: `API_URL = import.meta.env.VITE_API_URL || 'http://localhost:8080'` — Vite reads a `.env.production` file at build time in production, while local development silently falls back to `localhost:8080` with no code changes needed.

### Database questions

**"Describe your schema."**
Key points: three tables — `projects`, `architecture_results` (one-to-one with `projects`), `diagrams` (many-to-one with `projects`). Reference §6.1.

**"Why one-to-one for the architecture result but many-to-one for diagrams?"**
Key points: a project only ever needs one combined text result, whereas a project can accumulate many different diagram types over time, each a separate row. Confirmed by direct testing: calling `/generate` a **second time on the same project currently fails with a 500 error**, because the `unique=true` constraint on `architecture_results.project_id` rejects the second insert attempt rather than overwriting the existing row or creating a duplicate. This is a real, known limitation — worth mentioning proactively if asked, and a natural candidate for a future fix (e.g. update-if-exists logic in `OrchestrationService`).

**"Why Postgres specifically?"**
Key points: matches what was already being learned/used locally; strong relational fit for the clearly-related entities involved; Neon provided a good free managed option.

### AI/ML questions

**"What does the ML microservice actually do?"**
Key points: a TF-IDF + Logistic Regression classifier trained on a small hand-labeled dataset to categorize requirement sentences into 10 categories, exposed via its own FastAPI app. It originally also included a ChromaDB-based RAG component for retrieving architectural pattern context; that part was later removed after being identified as unused — never actually called by any agent during generation, and the single biggest source of Docker build friction earlier in the project. Be honest about the classifier too: it's **currently deployed and independently testable, but not actually called by the AI generation pipeline** — only its health-check endpoint is wired into the backend.

**"Why remove the RAG code instead of just leaving it there unused?"**
Key points: unused code that looks like a real feature is worse than no code at all in a portfolio project — it invites a question you can't answer well ("show me where this is used"). It was also actively costly to keep: the embedding-model download it required was the direct cause of several of the hardest Docker debugging sessions in the project (§7, problems #10–11). Removing it also meaningfully simplified the Dockerfile. The classifier was kept because it's smaller, genuinely tested, and demonstrably working on its own.

**"How did you handle prompt engineering for the agents?"**
Key points: each agent's prompt gives Gemini an explicit professional role/persona, the project's actual description and scale interpolated in, and an explicit expected output shape; for the one diagram type that kept producing invalid syntax (User Journey), the fix was adding a literal example block to the prompt rather than only describing the format in words.

**"How do you make sure the AI's output is usable/parseable?"**
Key points: for diagrams specifically, the raw Gemini response has any stray markdown code fences stripped programmatically before being stored, since prompts alone don't reliably prevent an LLM from adding them anyway.

### Debugging questions

**"Tell me about a hard bug you had to track down."**
Good candidates to discuss, using the STAR-ish shape (what broke, how you found it, what you changed): the Dockerfile missing its `CMD` instruction (§7 #11) or the cascading 22-error compile failure that was actually one duplicated interface (§7 #14) are both strong, concrete stories.

**"What's your general debugging approach?"**
Key points: isolate the smallest failing piece outside the full system (e.g. testing Gemini directly with `curl` before touching Java code); read the _actual_ error message/exception type rather than guessing; check whether a fix actually redeployed/rebuilt before assuming it failed again.

### Scalability questions

**"What would break first if this got a lot of traffic?"**
Key points: Gemini's free-tier rate limit (already hit during normal development/testing); the sequential (not parallel) agent calls, making each generation slower than necessary under load; no pagination on the project list; Render's free tier itself (sleep/cold-start behavior, and Render's own resource limits).

**"How would you scale the AI generation specifically?"**
Key points: parallelize the 4 core agent calls; consider a paid Gemini tier or a queueing system to smooth out bursts; cache results for identical inputs.

### Security questions

**"Is there authentication?"**
Key points: honestly, no — every endpoint is public. This is a clearly stated, known limitation, not something to overstate or hide.

**"How do you protect your API keys?"**
Key points: `GEMINI_API_KEY` is never hardcoded — read from an environment variable locally and set as a Render environment variable in production; a real incident occurred where a database password was accidentally pasted into a chat conversation, and the correct response (resetting the credential immediately) is worth describing as an example of taking credential exposure seriously even in a low-stakes learning project.

**"What does your CORS setup actually protect against, and what doesn't it protect against?"**
Key points: it restricts which _browser-based frontend origins_ can call the API; it does **not** prevent direct API calls via `curl`, Postman, or any non-browser client, since CORS is a browser-enforced restriction, not a server-side access control.

### "Why did you do it this way?" questions

**"Why not just write 17 separate diagram-generation functions?"**
Key points: covered in §8 — data-driven design (registry) over code duplication.

**"Why didn't you add authentication if this is meant to be a real deployed app?"**
Key points: honest answer — the priority was proving the core AI-orchestration and full-stack-deployment skills first; authentication is explicitly listed as a next step, not something forgotten.

**"Why Docker Compose locally but three separate Render services in production, instead of one combined deployment?"**
Key points: Docker Compose is for local multi-container orchestration; Render's free tier is structured around individual web services, so each of the three components (ML service, backend, frontend) became its own Render Web Service, each with its own root directory in the same monorepo.

### Difficult follow-up questions

**"If the classifier isn't actually used in generation, why keep it at all?"**
An honest answer should acknowledge this directly: it demonstrates a real, independently working microservice — training a model, exposing it over a clean API, deploying it separately — and was the very first piece of the project built and deployed. A related, larger RAG component had the same "built but unused" problem and, rather than leave it as unexplained dead weight, it was deliberately removed once identified. The classifier was kept specifically because it's small, genuinely tested, and honestly describable — connecting it into the actual agent prompts is accurately described as unfinished work, not a hidden or forgotten feature.

**"What would you change if you rebuilt this from scratch?"**
Reasonable, defensible answer: parallelize the agent calls from the start; split the controller earlier rather than letting it grow into one large file; wire the RAG retrieval into the prompts from the beginning rather than treating it as a separate, later step; write tests alongside features instead of relying entirely on manual testing.

**"How confident are you that the AI-generated architectures are actually good?"**
Honest answer: they're a genuinely useful _first draft_, produced by a capable general-purpose model with role-specific prompting and scale awareness, but they are not verified against real-world engineering best practices by any automated check, and are not a substitute for review by an experienced engineer — this is a reasonable, defensible framing rather than overclaiming the tool's authority.
